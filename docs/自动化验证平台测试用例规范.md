# 自动化验证平台测试用例规范

## 1. 使用场景

这份规范同时适用于两类测试来源：

1. 已有产品需求、页面原型或需求文档的回归测试。
2. 直接针对开发完成的页面、接口、Agent、Skill、工作流或其他功能进行验收。

开发完成后，开发或测试人员可以直接按本文输出标准测试包；测试人员也可以先在平台创建测试项目和测试需求，再导入测试包。两种方式最终都归档为同一套测试资产。

## 2. 固定层级

```text
测试项目 → 测试需求 → 测试用例 → 执行结果
```

- 测试项目：隔离业务域或测试资产，例如“会员改版”“开放平台”“Agent / Skill”。
- 测试需求：一次可独立验收的功能范围、回归目标或发布批次。
- 测试用例：一个可独立执行、可判定结果的测试场景。
- 执行结果：某次运行的状态、耗时、实际结果、轨迹和截图。

产品需求目录中的主需求/子需求不等于测试需求。测试需求可以关联产品需求，也可以只关联页面、功能、接口或开发任务。

## 3. 测试需求输出要求

测试需求至少提供以下信息：

| 字段 | 要求 |
| --- | --- |
| `id` / `key` | 稳定、唯一，建议使用 `TR-业务或版本-序号` |
| `name` | 能表达本次测试范围和回归目标 |
| `target` | 被验证的页面、功能、接口、Agent、Skill 或工作流 |
| `pagePath` | 页面路径、功能树路径或接口/能力路径；没有页面时填写功能路径 |
| `version` | 版本号、发布日期或发布批次 |
| `scope` | 本次覆盖范围、重点变化和明确不覆盖内容 |
| `environment` | 测试环境、账号环境、浏览器或服务版本 |
| `preconditions` | 登录态、依赖服务、权限、配置和数据准备 |
| `testData` | 测试账号、套餐、商品、文件、Prompt、请求参数等 |
| `authMode` | 可选；`none`、`bearer` 或 `storage-state`，只描述认证方式，不保存密钥 |
| `authProfile` | 可选；认证配置名，例如 `moni-user`，不填写 Cookie、Token 或密码 |

如果尚未建立测试需求，可以先在 `/agent-eval` 中创建需求，再导入只包含 `cases` 的文件；如果开发直接输出完整测试包，则应同时提供 `requirement` 和 `cases`。

## 4. 测试用例输出要求

每条用例必须能被单独执行和判定，至少提供：

| 字段 | 要求 |
| --- | --- |
| `id` | 稳定、唯一，不随排序变化 |
| `kind` | `Page`、`Feature`、`Agent`、`Skill`、`API` 或 `Workflow` |
| `mode` | `api` 或 `browser` |
| `target` | 具体测试对象或能力路径 |
| `name` | 用结果导向的短句描述场景 |
| `input` | 用户输入、请求参数或触发条件 |
| `expected` | 可观察、可判定的期望结果，避免“正常”“符合预期”等空泛描述 |
| `priority` | `P0` 主流程/阻断、`P1` 重要分支、`P2` 边界或补充场景 |
| `tags` | 便于筛选的标签，例如主流程、异常、权限、兼容性、回归 |

按执行方式补充：

- `browser`：提供 `browser.steps`，步骤使用 `goto`、`click`、`fill`、`press`、`waitForText`、`waitForSelector`、`screenshot`；同时提供 `allowedHosts`。`click`、`fill`、`press`、`waitForSelector` 必须提供稳定的 `selector`；其中 `press` 还必须提供 `key`，例如 `{ "action": "press", "selector": "[data-testid=\"search-input\"]", "key": "Enter" }`，不能省略 `selector` 后直接按当前页面焦点。选择器优先使用 `data-testid`、稳定 `id` 或明确的语义定位，禁止依赖脆弱的层级和随机 class。`goto.url` 必须填写真正要验证的业务页面地址，平台不会自动使用当前浏览器打开的页面。
- 如果导入的用例没有单独声明 `ignoreHTTPSErrors`，可以在测试需求工作台的“接口配置”中开启“忽略测试环境 HTTPS 证书”；该开关只应对 local/测试环境使用，生产地址保持关闭。
- 如果浏览器页面需要登录，测试需求应使用“浏览器认证与登录态”配置，选择 `storage-state` 并引用认证配置名；登录态文件由本地 Runner 读取，不要把 Cookie、密码或 Token 写入 JSON。浏览器用例本身只声明前置条件和业务页面步骤。
- 如果步骤字段不完整，属于用例编写错误，应在导入前修正；Runner 会明确提示缺少 `selector` 或 `key`，不会把 `locator('undefined')` 当作业务断言失败。
- `api`：提供 `api.endpoint`、`api.method`，必要时补充 `headers`、`body`、`expectedStatus`、`expectedText` 或结构化断言。
- 两种方式都可以补充 `preconditions`、`testData` 和 `pagePath`，用于覆盖单条用例的特殊准备条件。

### 4.1 浏览器地址、白名单与 HTTPS 证书

浏览器用例需要同时处理“访问哪个地址”“允许访问哪个域名”“是否信任测试环境证书”三个问题：

| 配置 | 写在哪里 | 写法 | 说明 |
| --- | --- | --- | --- |
| 真实访问地址 | `browser.steps[].url` | 完整 `http://` 或 `https://` URL | 必须是实际被测页面，不是测试平台工作台地址 |
| 域名白名单 | `browser.allowedHosts` | 只写域名，例如 `local.chuangkit.com` | 不要写协议、端口、路径或查询参数 |
| 忽略测试证书 | `browser.ignoreHTTPSErrors` | `true` 或 `false` | 仅本地/测试环境自签名证书使用，生产环境默认 `false` 或省略 |

例如，`local.chuangkit.com:3007` 使用测试证书时：

```json
{
  "mode": "browser",
  "browser": {
    "ignoreHTTPSErrors": true,
    "allowedHosts": ["local.chuangkit.com"],
    "steps": [
      {
        "action": "goto",
        "url": "https://local.chuangkit.com:3007/custom-design?from=enterprise_service&category=social"
      },
      {
        "action": "waitForSelector",
        "selector": "body",
        "state": "visible"
      },
      {
        "action": "screenshot",
        "name": "定制设计页面"
      }
    ]
  }
}
```

`ignoreHTTPSErrors: true` 只表示忽略证书校验，不代表允许访问任意地址；域名仍必须命中 `allowedHosts`。如果导入的用例没有单独设置该字段，可以在工作台“接口配置”中打开“忽略测试环境 HTTPS 证书”，它会作为本次运行的全局配置传给 Runner。标准测试包本身仍只输出 `requirement` 和 `cases`，不要把工作台运行配置混入顶层。

### 4.3 登录态与认证配置

认证信息属于测试需求的运行配置，不属于单条用例的业务输入：

| 场景 | 工作台配置 | 用例要求 | 说明 |
| --- | --- | --- | --- |
| 无认证 | `无需登录态` | 无 | 适用于公开页面或公开接口 |
| API Token | `Bearer Token` / `API Key` | `api.endpoint` 写真实业务接口 | Token 只在工作台运行配置中填写，JSON 不保存密钥 |
| Moni 浏览器登录 | `Moni 登录态文件` | `mode: browser`，补充登录前置条件 | Runner 使用 Playwright `storageState` 加载 Cookie 和 LocalStorage |

浏览器登录态配置至少包含：

- 认证配置名，例如 `moni-user`；
- 本地 Runner 可读取的 `storageState` 文件路径；
- 登录态验证状态；
- 过期或跳转到登录页时的明确错误提示。

登录态文件只能存放在本地安全目录，不要提交到 Git。测试用例中不要填写账号密码、Cookie、Token 或绝对路径。浏览器用例应直接访问登录后的真实业务页面；登录接口不是业务页面用例的 `goto` 地址。

### 4.2 浏览器步骤字段

| 步骤 | 必填字段 | 示例 | 判定 |
| --- | --- | --- | --- |
| `goto` | `url` | `{ "action": "goto", "url": "https://test.example.com/page" }` | 地址可访问且通过白名单 |
| `click` | `selector` | `{ "action": "click", "selector": "[data-testid=\"submit\"]" }` | 元素存在并可点击 |
| `fill` | `selector`、`value` | `{ "action": "fill", "selector": "[data-testid=\"keyword\"]", "value": "海报" }` | 元素存在并完成输入 |
| `press` | `selector`、`key` | `{ "action": "press", "selector": "[data-testid=\"keyword\"]", "key": "Enter" }` | 指定元素接收按键 |
| `waitForSelector` | `selector` | `{ "action": "waitForSelector", "selector": "body", "state": "visible" }` | 元素达到指定状态 |
| `waitForText` | `text` | `{ "action": "waitForText", "text": "保存成功" }` | 页面出现目标文本 |
| `screenshot` | 无；可选 `name` | `{ "action": "screenshot", "name": "保存成功" }` | 保存当前页面截图 |

`press` 不能只写 `key`。如果业务确实是对当前焦点按键，需要先通过 `click` 或其他步骤明确焦点元素；不要依赖不可复现的页面默认焦点。

## 5. 标准 JSON 包

文件建议命名为 `测试需求key-测试包版本.json`，格式固定为 `ckt-eval/v1`：

```json
{
  "format": "ckt-eval/v1",
  "requirement": {
    "id": "TR-V2610-01",
    "key": "TR-V2610-01",
    "name": "会员页面配置 - 套餐切换回归",
    "target": "会员页面配置",
    "pagePath": "创客贴管理后台 > 会员页面配置",
    "version": "V2610",
    "scope": "套餐切换、数据刷新和异常提示",
    "environment": "测试环境",
    "preconditions": "已登录后台；依赖服务已启动。",
    "testData": "个人专业版套餐",
    "authMode": "storage-state",
    "authProfile": "moni-user"
  },
  "cases": [
    {
      "id": "TC-TR-V2610-01-001",
      "kind": "Page",
      "mode": "browser",
      "target": "会员页面配置 > 套餐切换",
      "name": "切换套餐后内容刷新",
      "input": "进入页面并切换到个人专业版。",
      "expected": "套餐名称、价格、积分和权益内容同步刷新。",
      "priority": "P0",
      "tags": ["页面改版", "主流程"],
      "browser": {
        "ignoreHTTPSErrors": false,
        "steps": [
          { "action": "goto", "url": "https://admin.example.com/member-page-config" },
          { "action": "click", "selector": "[data-testid=\"member-type-select\"]" },
          { "action": "click", "selector": "[data-testid=\"member-type-personal-pro\"]" },
          { "action": "waitForText", "text": "专业版" },
          { "action": "screenshot", "name": "套餐切换完成" }
        ],
        "allowedHosts": ["admin.example.com"],
        "textContains": "专业版"
      }
    }
  ]
}
```

平台也兼容历史导入方式：JSON 数组、JSONL 和 CSV。历史格式没有 `requirement` 元数据时，先在平台选择对应测试需求，再导入用例；标准包中的需求元数据会自动回填当前测试需求。

## 6. 执行结果判定

- `通过`：步骤执行完成，接口/页面断言满足期望结果。
- `未通过`：步骤执行完成，但状态码、文本、URL 或其他业务断言不满足期望结果。
- `执行失败`：Runner 无法完成步骤，例如地址不可访问、证书错误、元素超时、缺少 `selector`/`key`、Runner 离线或接口请求异常；这类结果不能直接当作业务功能不通过。

## 7. 用例设计检查清单

- 是否明确测试对象，而不是只写“验证功能是否正常”？
- 是否覆盖主流程、关键分支、异常、权限和边界？
- 输入、步骤和期望结果是否能让另一个人独立复现？
- 期望结果是否包含页面文案、状态、字段值、接口状态码或结构化字段？
- 浏览器场景是否使用稳定选择器并限制访问域名？
- 是否补充了测试环境、前置条件和必要测试数据？
- P0 用例是否足以覆盖发布阻断路径，P1/P2 是否避免与其他用例重复？
